# LogicIR Core Schema v0 Draft

This directory is for the target-neutral LogicIR core schema. Core contains only the semantic relations that must be preserved across software runtimes, Verilog HDL, tools, analyzers, editors, and future projection targets.

## Scope

Core schema must represent:

- Bounded LUs and local LUIs.
- X/Y execution-plane kind: Combinational, Sequential, Stateful, Structural.
- Ports, pins, port discipline, addressable endpoint references, in-plane connections, and structural composition organization.
- Requirement services and requirement units.
- Fulfillment relations, including Closure fulfillment and upstream lineage fulfillment.
- Closure cores and same-key forwarded port declarations.
- Target references for LU-defined, external, and requirement-backed manifestations.
- Core invariants needed to determine whether the represented object is the same logical topology.

## Out of Scope

Core must not encode:

- JS Promise/Thenable or async runtime mechanics.
- Subscription/listener implementation details.
- Runtime state store handles.
- Hook, provider, or local plugin implementation APIs.
- Verilog clock/reset, module elaboration, or HDL lowering details unless expressed as target-neutral logical topology.

## Files

- `packages/core/src/types.ts`: TS-first authoring source for core protocol
  data shapes.

Add glossary, model, invariants, wire-shape, examples, or generated formats only when that work starts and the file can carry real design content.

## Authoring Discipline

Schema TypeScript source is protocol authoring, not a TypeScript library API.
Do not use TypeScript generics or utility types as schema abstraction. This
includes `Base<T>`, `Record<K, V>`, `Exclude<T, U>`, `Pick`, `Omit`,
`Partial`, and similar TS-only conveniences. Spell protocol shapes out with
serializable object, union, intersection, array, and index-signature types. A
little repetition is preferable to a schema shape that only exists in
TypeScript's type system.

## Essay Relationship

This draft refines the representative schema sketch in `docs/essay.md` without changing the X/Y/Z model. X remains the unit-level boundary-drive axis; `Port.contact` is contact-level capability: `pull`, `push`, or `property`. A `property` contact is retained-current and BehaviorSubject-like: it is readable as the latest current value, notifies updates, and must have an initialized current value supplied by the declaring unit, its source, or an explicit preserving adapter. The submitted essay text does not need to be edited for this draft refinement.

## Current Shape

- `PortSurface` is a kind-specific object, not a flat map. It uses `inputs`, `outputs` where legal, and where legal a distinct `result` slot. Combinational ports have `inputs + result` only. There is no port `role`; result semantics are represented by the `result` field itself.
- `LUCore` is a discriminated union by `kindOrganization.kind`. The containing LU kind constrains which LUI kinds may appear in its single `luis` map.
- Sequential organization is the minimal ordered list `steps: LUIId[]`. Guards, branches, async policy, return behavior, and addressable control-flow nodes belong in features or `LUCore.extensions`.
- Structural composition uses anchors and outlets. `compositionSurface.outlets` is a set-like `CompositionOutletKey[]`; anchors carry `shape` and `required`.
- Structural LU/closure cores declare `exportAnchors`, `externalOutlets`, `exportAnchorFills`, and `luiFills` in the structural `kindOrganization` branch. LU/closure export anchors are single anchors; non-single composition is supplied through structural LUI anchors and `luiFills`.
- Requirement services may be inline or external. External services and external LUI targets use `namespace + key`; registry lookup and realization details are outside core.
- Each `LogicUnit` declares a `features` manifest. Extension records reference
  that manifest by local `featureKey`; they do not repeat feature
  `namespace/key` directly.
- Extensions attach to stable owner or relationship nodes. Kind-specific metadata for `kindOrganization` internals is expressed through owner-level extensions, usually `LUCore.extensions`, using selectors inside the extension payload.

## Core Invariants

| ID | Area | Invariant |
| --- | --- | --- |
| CORE-001 | Identity and keys | `id` is the opaque machine/editor identity used for graph addresses, references, diffing, migration, and visual-editor persistence. It must not carry semantic meaning. `key` is reserved for stable semantic names in a declared namespace or contract surface, such as ports and requirement service/unit names. |
| CORE-002 | Typed identity | Each addressable machine entity has its own id type, such as `LUId`, `LUIId`, `ClosureId`, and `ConnectionId`. Do not use a generic identity mixin that erases the entity kind. |
| CORE-003 | Map identity | When an entity is stored in a keyed object map such as `{ [id: LUIId]: LUI }`, the map key is the entity identity. The entity body must not repeat the same id field unless it is not keyed by an enclosing object. This includes LUIs, closures, and connections. |
| CORE-004 | LogicUnit boundary | `LogicUnit` is the schema body for one bounded LU. It does not declare its own registry identity or catalog key; LU maps, package indexes, file names, and import aliases belong to the application/tooling layer that carries the `LogicUnit`. |
| CORE-004A | Feature manifest | `LogicUnit.features` is the LU-local manifest of feature dependencies used by its extension records. A `FeatureUseKey` is a local alias, not the feature identity. The manifest entry inlines the feature namespace, key, and optional version so an LU remains independently portable outside any document/package container. Feature-level behavior configuration belongs in feature-owned extensions, profile policy, or execution bindings, not in the manifest. |
| CORE-005 | LU kind | `LUCore.kindOrganization.kind` is the single source of truth for the LU execution-plane kind. `LogicUnit` must not repeat this kind at its wrapper level. |
| CORE-006 | Required empty collections | Core collection fields must be present when their slot exists, even when empty. Use `{}` for empty maps and `[]` for empty lists in fields such as `ports.inputs`, non-combinational `ports.outputs`, `requirements`, `closures`, `fulfillments`, structural `compositionSurface.outlets`, structural `externalOutlets`, structural `exportAnchorFills`, structural `luiFills`, nested `requirements`, and `forwardedPortKeys.inputs/pushOutputs`. Optional fields are reserved for meaningful absence, such as whole-port `payloadPath`, missing sequential `ports.result`, missing `pins`, or no extension records. Combinational ports do not declare `outputs` at all. |
| CORE-007 | In-plane flow | Ports and connections express ordinary data or signal interaction only. Requirement fulfillment and structural composition must not be encoded as a connection. |
| CORE-008 | LUCore kind union | `LUCore` is a discriminated union by `kindOrganization.kind`. It keeps one `luis` map in the wire shape, but the allowed LUI value kinds are constrained by the containing LU kind: combinational cores contain only combinational LUIs; stateful cores contain combinational or stateful LUIs; sequential cores contain combinational, stateful, or sequential LUIs; structural cores contain combinational, stateful, or structural LUIs. Cross-reference existence and target compatibility are still validator responsibilities. |
| CORE-009 | Single-driver target | Within one `LUCore.connections` map, target driving is checked by overlapping `Connection.to` endpoint addresses (`owner`, `port`, and `payloadPath`), not only by whole-port identity. Fan-out from one `from` endpoint is allowed. Fan-in, multi-driver, partial-merge, or resolver behavior must be represented by an explicit LUI, or by a feature extension declared required or conditional-required by the selected profile. |
| CORE-010 | Connection direction | Endpoint direction is derived from `EndpointRef.port.kind` plus `PortOwner`, while `Connection.from`/`Connection.to` are relative to the containing `LUCore` graph. A root `lu` port or closure `input` endpoint is a source inside its containing core, because data enters the core through that boundary; a root `lu`/closure `output` or `result` endpoint is a sink. A child `lui` `input` endpoint is a sink inside the parent core, and a child `lui` `output` or `result` endpoint is a source. `payloadPath` does not change the containing endpoint slot. |
| CORE-011 | Structural composition | Composition belongs inside the structural `LUCore.kindOrganization` branch. Composition points are not ports, do not use connection edges, and do not need their own machine ids. |
| CORE-012 | Composition declarations | Structural composition uses two primitives: anchors and outlets. `CompositionAnchor` has `shape` and `required`; outlets are declared as `CompositionOutletKey[]` because core outlets carry no value shape beyond their key. For a structural LU or closure core, `exportAnchors` are exported single anchors on the surrounding structure and only carry `required`. `externalOutlets` declare outlets visible inside the current structure that are supplied by the parent composition context when this structure is instantiated. For a structural LUI instance, `compositionSurface.anchors` are the instantiated form of the target's `externalOutlets` and are filled by the parent, while `compositionSurface.outlets` are outlets that can be placed into the current LU/closure's anchors. |
| CORE-013 | Composition external outlets | An external outlet is an outlet declaration inside the current structural unit, but it resolves to an anchor when this unit is instantiated as a LUI and filled by its parent. It is not a port. The external outlet's `shape` constrains the value supplied through the parent's `luiFills`; collection or map composition must be represented by the filling `CompositionValue.collection` or `CompositionValue.map`, not by adding nested external outlet structure. Its `required` flag declares whether the parent must provide a binding when the structural LUI is instantiated. |
| CORE-014 | Composition bindings | `exportAnchorFills` binds the current structural LU or closure export anchors to single composition leaves. A `lui-outlet` leaf is an outlet from a child LUI and references one child LUI outlet by `luiId + outletKey`; an `external-outlet` leaf references one `externalOutlets` declaration by `outletKey`. Neither leaf carries child LUI anchor fills. Empty maps represent no bindings. Missing required bindings are validator errors. |
| CORE-015 | Empty composition leaf | `CompositionLeaf.kind === 'empty'` is an explicit empty/null composition value. Missing binding means unbound; `empty` means bound-to-empty. Missing required anchor bindings are validator errors, while explicit `empty` is allowed unless a feature contract or validator rule rejects it. |
| CORE-016 | Composition shape | Structural `exportAnchors` on the current LU or closure are always single anchors, so their declarations do not store a `shape` field. Non-single composition belongs in structural LUI anchors and is supplied through `luiFills`. Nested collection/map structure must be represented by an intermediate structural LUI, not by anonymous nested containers. A common exposed anchor key may be `root`, but `root` is not a core field name. |
| CORE-017 | Composition shape match | Each `exportAnchorFills[anchorKey]` must be a `CompositionLeaf` because current LU/closure export anchors are single anchors. Each `luiFills[luiId][anchorKey]` must match the resolved child LUI anchor's `shape`: `single` accepts only a `CompositionLeaf`, `collection` accepts only `CompositionValue.kind === 'collection'`, and `map` accepts only `CompositionValue.kind === 'map'`. |
| CORE-018 | Child LUI fills | `luiFills[luiId]` binds anchors exposed by that child LUI instance, independent of how many of the child's outlets are referenced by `lui-outlet` leaves. The referenced child LUI must resolve to a structural kind with a `compositionSurface.anchors` surface. Each fill key must exist in that resolved anchor surface, and each fill value must match the anchor's `shape`. Required child anchors must be filled unless a feature rule declared required or conditional-required by the selected profile declares another policy. |
| CORE-019 | Child LUI outlets | A `lui-outlet` leaf references one outlet of one child LUI. The referenced child LUI must resolve to a structural kind, and `outletKey` must exist in that child LUI's resolved `compositionSurface.outlets` key array. `compositionSurface.outlets` is set-like and must not contain duplicate keys. A structural child may expose multiple outlets; a single leaf references only one of them. |
| CORE-020 | LUI target | A `LUI.target` identifies what the LUI manifests. It does not by itself fulfill requirements. |
| CORE-021 | LUI kind | `LUI.kind` declares the manifestation kind visible in the parent core. For `lu` targets it must match the target `LUCore.kindOrganization.kind`; for `requirement` targets it must match the target `RequirementUnit.kind`; for `external` targets it is the core-visible kind contract. Structural LUIs must carry a resolved `compositionSurface`; non-structural LUIs must not carry one. A structural LUI targeting a requirement unit resolves its composition surface from that structural `RequirementUnit` contract. |
| CORE-022 | LUI composition surface | `LUI.compositionSurface` is the owner-local resolved composition surface for a structural LUI, analogous to `LUI.ports` for connection endpoints. It records the child LUI's `outlets` and `anchors` as seen by the parent core, so validators, analyzers, and projection compilers do not need to consult the target registry to check local composition references. Outlet keys do not carry `shape` or `required`; anchor shape and requiredness live on LUI `anchors`, while LU/closure `exportAnchors` are implicitly single. Contract-level extensions may describe surface-wide feature semantics without giving each outlet its own value object. |
| CORE-023 | Endpoint refs | `EndpointRef` is a logical endpoint address for connections, not a port declaration. It is `PortOwner` plus an `EndpointPortRef`, optionally plus `PayloadPath`. `EndpointPortRef` selects `input(key)`, `output(key)`, or the distinct `result` slot. Closure endpoints are addressed by `closureId` only because closures are keyed in `LUCore.closures`. |
| CORE-024 | Port pins | `Port.pins` optionally declares one level of pin surface inside a port, including a distinct `ports.result` slot when that result surface needs first-level addressing. `indexed` pins model array-like or bus-like contacts; `keyed` pins model named fields. Pins are not independent ports and inherit the containing port's contact kind and endpoint slot. |
| CORE-025 | Payload path | `EndpointRef.payloadPath` is a logical payload path under a port. Missing `payloadPath` means the whole port or whole `result` slot. A path can address nested payload structure, such as object fields, array items, bus lanes, result pins, or wrapped bus fields, without exploding them into independent ports. |
| CORE-026 | Payload path validation | When `payloadPath` is present and `Port.pins` is declared, the first segment must match the one-level pin surface. Later segments remain a logical nested payload address for the target LUI, feature extension, projection compiler, or execution engine and are not interpreted as nested core pins. Use intermediate LUIs when deeper payload structure must become explicit topology, carry different contact kind, or need independent identity. |
| CORE-027 | LUI port surface | `LUI.ports` declares the LUI's owner-local port surface inside the parent core. Connections to a LUI must reference this local port surface, not the target registry directly. |
| CORE-028 | Target port compatibility | For `lu` and `requirement` targets, each `LUI.ports.inputs` key, each declared `LUI.ports.outputs` key, and the `result` slot where legal must exist on the target interface in the same slot with the same key. LUI-level port aliasing or renaming is not core schema semantics. |
| CORE-029 | External port contract | For `external` targets, `LUI.ports` is the core-declared boundary contract for the externally realized target. The external target registry may add realization details, but it must not silently change the declared port discipline. |
| CORE-030 | Port discipline preservation | For `lu` and `requirement` targets, a LUI port must preserve the target port's contact kind and endpoint slot unless a selected profile requires a feature extension point or later adapter schema that explicitly declares otherwise. |
| CORE-031 | Result slot | Combinational ports must declare one `ports.result` slot and must not declare ordinary `ports.outputs`. Sequential ports may declare one optional `ports.result` slot in addition to push outputs. `result` is not a port `role` and is not part of `ports.outputs`. It is still a pull port, so it may declare `pins`, and `EndpointRef.port.kind === "result"` plus `payloadPath` can address a whole result, a result pin, or a deeper result payload path. A sequential `result` is pull contact and externally latched by the caller after the sequence run; sequential ports cannot declare any other pull output. Stateful and structural ports do not have a `result` slot. |
| CORE-032 | Requirement target | A `requirement` target lets a declared requirement appear inside local topology while its satisfaction remains a Z-axis fulfillment relation. |
| CORE-033 | Requirement surface | `RequirementSurface` is the top-level requirement surface exposed by a LU. It is a service-keyed map whose entries are either inline service declarations or external service contract references. The containing map key is the local service key used by LUI targets and fulfillments. |
| CORE-034 | Nested and plain requirements | A top-level `RequirementUnit` may declare a `PlainRequirementSurface` for one more layer of nested requirements. `PlainRequirementSurface` entries may also be inline or external service contract references. `PlainRequirementUnit` must not declare further requirements; this keeps requirement nesting finite and graph-editor friendly. |
| CORE-035 | External requirement service references | An external requirement service entry references a predefined service contract by `namespace + key` and may include `version` to pin a concrete contract. Validators, projection compilers, or execution engines must resolve that contract before checking LUI target compatibility, ports, structural composition surface, fulfillment scope, units, and fulfillment shape. Core does not define the external contract registry or database lookup mechanism. |
| CORE-036 | Derived LUI requirement surface | A LUI's requirement surface is derived from its `target`, not stored on the LUI. For `lu` targets it comes from the target `LogicUnit.requirements`; for `requirement` targets it comes from the target `RequirementUnit.requirements`; for `external` targets it comes from the external registry or feature contract when such a contract exists. When a top-level `RequirementUnit` is manifested as a LUI, the LUI's `fulfillments` satisfy that unit's nested plain requirement surface, not the requirement target itself. |
| CORE-037 | Requirement keys | Requirement services and units are identified by their containing map keys. `RequirementService`, `PlainRequirementService`, `RequirementUnit`, and `PlainRequirementUnit` bodies must not repeat opaque ids. Structural requirement units must declare a `compositionSurface` contract with outlets and anchors; non-structural requirement units must not. External service contract keys identify registry contracts, not the local service key used in a LU's requirement surface. |
| CORE-038 | Requirement fulfillment scope | A resolved requirement service's `fulfillmentScope` declares the expected fulfillment shape: `independent-units` is fulfilled by a unit-level map, while `shared-service` is fulfilled by one service-level supplier. This is not the same as `LUKind.stateful`. |
| CORE-039 | Fulfillment shape match | A `RequirementServiceFulfillment.kind` must match the resolved target service's `fulfillmentScope`. Validators must reject `shared-service` fulfilled as independent units, and `independent-units` fulfilled as a service supplier. |
| CORE-040 | Independent unit fulfillment | `independent-units` services use `IndependentUnitsFulfillment.units`, where each unit has its own `UnitFulfillment`. This supports services whose units do not share supplier identity or state. |
| CORE-041 | Shared service fulfillment | `shared-service` services use one `UpstreamServiceSupplierFulfillment`. The upstream supplier is analogous to an object/service instance; units are resolved under that supplier, like methods on the same object. |
| CORE-042 | Fulfillment forms | Unit fulfillments are explicit local Closure fulfillments or upstream unit fulfillments. Service supplier fulfillments currently resolve to upstream service suppliers; local service suppliers require a future explicit supplier structure, not a plain Closure. |
| CORE-043 | Closure role | A Closure is a local boundary object stored in `LUCore.closures` and referenced by closure fulfillment. It is not itself a LUI and should not be modeled as ordinary child nesting. |
| CORE-044 | Closure fulfillment | A closure fulfillment points to a `closureId`; the closure body lives in `LUCore.closures`. |
| CORE-045 | Forwarded ports | Closure `forwardedPortKeys` declares which same-key inputs and push outputs from the Closure core are visible outside the Closure boundary. Forwarded ports are ordinary in-plane contacts, not requirement fulfillment paths. A Closure must not forward pull `result` or property output as an output. |
| CORE-046 | Forwarded port integrity | Each forwarded input key must exist in `Closure.core.ports.inputs`. Each forwarded `pushOutputs` key must exist in `Closure.core.ports.outputs` and resolve to `contact === 'push'`. The key visible outside the Closure is the same key as the inner core port. Forwarding does not rename ports or redeclare port discipline. |
| CORE-047 | Supply lineage | `reachabilityPath` is an ordered list of `ClosureId` values that records the Closure boundaries through which upstream supply is admitted. The current fulfillment site is implied by the containing LUI, so LUI steps are not encoded. Reaching the current/root supply environment is represented by an empty `reachabilityPath`, not by a LU step. |
| CORE-048 | External target | `external` targets refer to externally realized capabilities by `namespace + key` and may include `version` to pin a concrete target contract. The namespace identifies the external target registry or semantic space, and the key identifies a target inside that space. Core does not import host, package, native binding, primitive, module, or capability registry mechanics. |
| CORE-049 | Extensions | Features are capability units; extension records carry concrete node-level payloads under a local `featureKey` and extension `key`. `featureKey` must resolve in the containing `LogicUnit.features` manifest. Record-level required/optional status is not part of core. Feature definitions own extension points and payload schemas; profiles declare which feature/extension-point contracts are required for a pipeline, projection, or execution target. Profiles and stacks are outside the LogicIR object model. |
| CORE-050 | Runtime separation | Core schema must remain free of JS runtime details and Verilog HDL realization details. |
| CORE-051 | Extension attachment | Extensions should attach to stable owner or relationship nodes, such as `LogicUnit`, `LUCore`, `LUI`, `Port`, `Connection`, `Closure`, requirement services, service-level fulfillment relations, and unit fulfillment relations. Do not attach extensions to internal helper structures or child declarations covered by a parent owner, such as `RequirementUnit`, `PinSet`, `kindOrganization` branch internals, sequential `steps`, `CompositionLeaf`, or `CompositionValue`. Owner-level extension payloads may use selectors such as `unitKey`, `port`, or payload paths to point at an internal position. Extension support must not introduce ids where core does not otherwise need identity. |
| CORE-052 | Port contact kind | `Port.contact` describes contact-level capability, not the LU's X-axis coordinate. `pull` means the contact can be sampled/read as a value. `push` means arrival/change notification can cross the contact. `property` means a retained-current reactive contact: it is pull-readable, push-notifiable, and initialized. |
| CORE-053 | Property contact | `property` is the core form of the old `Property` behavior: notifications and later reads refer to the same latest logical value. Core does not decide whether the retained value is implemented at the source, sink, or an inserted adapter. Current v0 port surfaces permit property inputs only on structural ports and property outputs only on stateful ports. |
| CORE-054 | Connection contact compatibility | A connection's resolved source endpoint must provide the contact behavior required by the resolved target endpoint. Identical contact kinds are compatible by default. Any conversion between `pull`, `push`, and `property` requires an explicit adapter or feature rule that declares semantic preservation. |
| CORE-055 | Target path overlap | Two `Connection.to` endpoints overlap when they share the same `owner` and `port`, and one `payloadPath` is missing or one path is a prefix of the other. Overlapping target endpoints are invalid by default. This allows independent lane wiring such as `["x"]` and `["y"]`, but rejects whole-port plus sub-path driving, duplicate lane driving, and parent/child partial overrides such as `["a"]` with `["a", "b"]` unless the selected profile requires a merge/resolution feature rule. |
| CORE-056 | Path selector and remap | `Connection.from.payloadPath` is a source payload selector for pull/property flow and a source payload path filter/prefix for push/property notification flow. `Connection.to.payloadPath` is a target payload assembly location for pull/property flow and a target payload path prefix/remap for push/property notification flow. Payload paths perform addressing and remapping only; computation, filtering by value, packing/unpacking with semantics, or fan-in must be modeled as a LUI or declared by a feature extension required or conditional-required by the selected profile. |
| CORE-057 | Spatial slices | A structural LU's `exportAnchors` are named spatial slices. A common slice key may be `root`, but a structural LU may expose many slices, and a parent may reference different slices of the same child LUI independently. |
| CORE-058 | Slice participation | A slice's participating child LUIs and external outlets are derived from `exportAnchorFills[anchorKey]`, which is a single `CompositionLeaf`. If that leaf references a child structural LUI outlet, analyzers may recursively inspect that child's referenced `outletKey` to derive nested slice participation. Collection/map participation is discovered through explicit structural LUI anchors and `luiFills`, not by nesting values directly under the current LU's export anchor. |
| CORE-059 | Slice-local and cross-slice flow | `exportAnchors` define structural spatial boundaries; they do not by themselves assign every `Connection` to a slice. Projection compilers or analyzers may classify connections as slice-local, cross-slice, or shared by comparing endpoint owners with derived slice participation and by following payload-path usage. Ambiguous or target-specific partitioning must be handled by a feature extension or diagnostic, not guessed silently. |
| CORE-060 | Distributed slice projection | A projection compiler may lower a structural LU with `N` export anchors into `N` slice subsystems. This is a projection strategy, not a core requirement. The generated subsystems may introduce coordination contacts such as one push-notifiable `rx` input bus and one push-notifiable `tx` output bus while preserving the original core topology and connection identities. |
| CORE-061 | Slice bus routing | Cross-slice traffic should be represented as ordinary `Connection` records to addressed bus endpoints. A single `tx` or `rx` bus port can use `Port.pins` for first-level target/channel names and `EndpointRef.payloadPath` for nested message fields or bus lanes. Multiple connections may target the same bus port only when their target payload paths do not overlap under `CORE-055`; merge, resolver, packing, scheduling, placement, or transport guarantees require an explicit LUI or a feature extension required or conditional-required by the selected profile. |

## Port Discipline by LU Kind (Draft)

These rules are validation targets where they depend on ports and cross-references. The schema type already constrains LUCore kind-specific fields and the allowed LUI kind set for each containing LU kind.

| ID | LU kind | Draft discipline |
| --- | --- | --- |
| CORE-062 | `combinational` | Space-like, pull-driven logic. Inputs are pull contacts. `result` is the only output/result surface and is one pull contact, optionally split by `pins` and `payloadPath`. Combinational ports do not declare ordinary `outputs`. Progress, events, notifications, or other push surfaces require a different LU kind, an explicit surrounding adapter, or a feature/runtime mechanism outside combinational core ports. |
| CORE-063 | `sequential` | Time-like ordered progression. Progression is represented by `kindOrganization.steps: LUIId[]`, an ordered list of LUIs, not software await/no-await. Inputs are pull or push contacts. Outputs are push contacts. Optional `result` is one pull contact latched by the external caller after a sequence run; sequential cannot declare other pull outputs. |
| CORE-064 | `stateful` | Time-like resident state under external arrival. Inputs are pull or push contacts. Outputs are push or property contacts. Property outputs expose initialized durable/current state. Stateful ports do not accept property inputs; dependent ordering between stateful units should be expressed as sequential logic. |
| CORE-065 | `structural` | Space-like structure re-manifested under external arrival. Inputs are pull, push, or property contacts; property inputs model prop-like retained-current inputs. Outputs are push contacts only. Structural outlets remain in `compositionSurface`, not in ports. |

The exact legal port combinations remain draft until core examples and validators are introduced. Do not encode JS runtime scheduling terms such as await/no-await in these rules.
